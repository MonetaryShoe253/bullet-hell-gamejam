# Art Spec

The single source of truth for how art in this game is sized, coloured and
displayed. `tools/conform_art.py verify` enforces everything in here, so if you
change a rule, change it in this file *and* in `tools/art_manifest.json`.

## 1. The grid

The game runs at a **1920x1080 viewport** with the player `Camera2D` at
`zoom = Vector2(3, 3)`. That makes the true art resolution:

```
1920 / 3  x  1080 / 3   =   640 x 360 native pixels
```

**One texture pixel (texel) = one world unit = 3 screen pixels.** Everything
below follows from that one line.

> Verified: `Camera2D.zoom` ignores the scale of its parent node, so the
> Player's own scale does *not* multiply the zoom. Native res is 640x360, not
> 640/1.5. Do not "compensate" for player scale in the camera.

### The rule that actually matters

> **Every `Node2D` that draws a texture must have an integer `global_scale`.**

Not "roughly 1". Integer. `1.0` for almost everything, `2.0` for bosses. A
sprite at `scale = 0.375` samples one texel onto 1.125 screen pixels, so some
texels get 1 screen pixel and their neighbours get 2 -- that is the crawling,
mismatched-chunkiness look, and no amount of regenerated art fixes it.

Corollaries:

- Resize the **source art** to its final size. Never scale at runtime to fit.
- `region_rect` values must be whole numbers.
- Non-uniform scale (`Vector2(18.02, 19.5)`) is always a bug.
- `texture_filter = 1` (Nearest) everywhere. Project default is already Nearest.
- Transient tween scales during a spawn/despawn animation are exempt -- they are
  motion, not a resting state.

## 2. Canvas size ladder

Author on these sizes only. Sizes are canvas, not content.

| Role | Canvas | World size | Notes |
|---|---|---|---|
| Tile | 16x16 | 1 tile | Tileset grid |
| Bullet / pickup | 16x16 | 1 tile | |
| Player | 32x32 | 2 tiles | Was 68x68 crushed to 25.5 world px at 1.12 screen px/texel |
| Small prop | 32x32 / 32x40 | 2 tiles | Decorations; kept at native size, already on grid |
| Tall prop | 32x48 | 2x3 tiles | Pillars, vending machines |
| Enemy | 48x48 | 3 tiles | Boss = same art at integer `scale = 2` (was 2.4 / 2.6) |
| Wide prop | 64x48 | 4x3 tiles | Shopkeeper |
| Large decal | 80x80 | 5 tiles | Spawn indicator |
| Portal | 64x80 | 4x5 tiles | |
| UI / shop icon | 32x32 | -- | Displayed at 5x = 160px in `shop_ui.tscn` |

Anything not on this ladder needs a line added to this table and the manifest.

### Ground contact

Props that stand on the floor are anchored **bottom-centre** in their canvas so
they sit on the tile they occupy. Characters, bullets and decals are anchored
**centre**. This is the `anchor` field in the manifest.

## 3. Palette

`assets/palette/wingpunk40.gpl` -- 40 colours, ten ramps. Derived from the
histogram of the game's existing pixel art (fried gold, sauce red and warm
browns dominated it), then curated into even steps.

`GOLD_3` is `#F7912C` **exactly** -- the player's hoodie orange and the single
most common colour in the game. It is pinned, not approximated: an earlier draft
of this palette rounded it away and every character in the game turned brown.

**Every sprite is force-mapped to this palette.** This is what buys visual
consistency across art from different sources -- more than any prompt wording.
A sprite generated by a local Stable Diffusion model, an old PixelLab asset and
a hand-drawn tile all become the same "art style" once they share 40 colours and
one grid.

Hue is load-bearing, not decorative:

| Ramp | Meaning |
|---|---|
| `COOL_*` | **Player-owned** -- bullets, energy, dash trail |
| `SAUCE_*` | **Enemy-owned** -- bullets, damage numbers, telegraphs |
| `GOLD_*` | The wing/batter identity -- pickups, hero surfaces, coins |
| `VIOLET_*` | Boss and cursed/rare tier (matches the existing `Color(0.75, 0.3, 0.95)` boss tint) |
| `STEEL_*` | Stainless kitchen equipment -- fryers, counters, cleavers, armour |
| `SKIN_*` | Faces and hands. Without this ramp every character's face snaps to grey |
| `WOOD_*`, `CREAM_*`, `GREEN_*`, `INK_*` | Environment, ranch/paper, celery/lettuce, outlines |

> **Readability note, unresolved:** the player's projectile is a golden
> drumstick and the slime's is an orange flame. Mid-fight they are very hard to
> tell apart, which is a gameplay problem rather than an art one. Forcing the
> drumstick into `COOL_*` fixes it instantly (add `"ramp": "COOL"` to the
> `player_bullet` group and re-run `conform`) but costs the chicken theme; a
> `COOL_3` rim light on a still-golden drumstick probably reads better. Left as
> a design call -- the lever is one manifest field.

Outlines use `INK_0`. Semi-transparent pixels are not allowed: alpha is
thresholded to fully opaque or fully clear, or edges shimmer when the sprite
moves at 3x zoom.

### Why the pipeline order matters

The palette snap happens at **source resolution, before any downscale**, and the
downscale then picks the *most common* palette colour in each source block
rather than averaging. Averaging first blends a sprite with its own dark outline
and invents colours that appear nowhere in the artwork -- `#F7912C` hoodie plus
near-black outline averages to a muddy brown that then snaps to `WOOD_2`, and
`#F8C7B0` skin averages to grey. Both happened on the first run of this pipeline.
Snap first, then vote.

## 4. Theme

Fast-food kitchen, chicken-wing forward. Concretely:

- **Environment:** deep fryers, sauce vats, walk-in freezers, prep counters,
  tile floors with grout, grease-stained concrete, crates of wings.
- **Enemies:** food that fights back -- the existing burger / taco / pizza /
  sauceblob line. New enemies should be food, not fantasy.
- **Player:** the mascot. Weapons are kitchen implements and wings.
- **Pickups:** the existing sodas (Cluck Cola, Ranch Rush, Wing Sauce Fizz),
  ranch cups, celery.

The medieval dungeon tileset used to be the biggest theme break in the game.
It has been replaced by `assets/Dungeon/kitchen_tileset.png`, generated by
`tools/make_kitchen_tileset.py` -- see section 6. Nothing references
`assets/2D Pixel Dungeon Asset Pack/` any more; the whole folder can be
deleted.

## 5. Lighting

Single light source, **top-down and slightly front**. Highlights on upward-facing
surfaces, shadow on the underside, one-pixel `INK_0` contact shadow where an
object meets the floor. No cast shadows with direction -- they will not agree
between assets from different sources.

## 6. The tileset

**Done** -- `assets/Dungeon/kitchen_tileset.png`, drawn by
`tools/make_kitchen_tileset.py`.

### Why it is generated by code, not by a model

Tilesets are the one art job where a generator model is the wrong tool. Every
cell edge has to line up with its neighbours pixel-exactly, and the two plain
floor variants have to tile against themselves in any arrangement, because
`DungeonRenderer` scatters them by spatial hash. Diffusion models do not do
seams -- you would get 37 attractive, unusable images and spend longer repairing
joins than drawing them. Commercial kitchen surfaces are also the most
code-friendly subject available: quarry tile and grout, stainless panels,
rivets, vent slats. Regular geometry is exactly what code draws better than a
model, and it costs nothing and re-renders instantly.

### The layout is not negotiable

`scenes/dungeon/dungeon_renderer.gd` hardcodes which atlas cell means what.
37 cells are used -- a 6x6 block plus `SOLID_ROCK`:

```
      col0     col1     col2     col3     col4     col5
row0  cvx_NW   N-wall   N-wall   N-wall   N-wall   cvx_NE
row1  W-wall   flr NW   flr N    flr N    flr NE   E-wall
row2  W-wall   flr W    floor    floor    flr E    E-wall
row3  W-wall   flr SW   flr S    flr S    flr SE   E-wall
row4  cvx_SW   S-wall   S-wall   S-wall   S-wall   cvx_SE
row5  ccv_NW   S-wall   S-wall   ccv_NE   ccv_NW   ccv_NE
(8,7) SOLID_ROCK
```

"N-wall" is a wall cell with floor to its *south* -- the face you look at
across the top of a room. The 25 wall cells carry collision; the 12 floor cells
do not. Cells (0,0) and (5,0) do double duty as both a side wall and a convex
corner, so they have to work in both roles.

### The atlas is not just terrain

`scenes/dungeon/dungeon_map.gd` also paints **props** onto `PropLayer` from
hardcoded atlas coordinates that all sit *outside* the 6x6 terrain block:

| Constant | Cells | What it is |
|---|---|---|
| `PROP_LADDER` | (9,3) | The level-exit hatch. Marks the start room and the stairs cell -- **the only signal the player gets that a level is finished** |
| `PROP_GATE` | (6,6) (7,6) | The shutter dropped across a doorway while a room is locked |
| `PROP_CANDLE` | (5,9) | Warmer flanking the start room and shop counter |
| `PROP_BONES` | 4 cells | Boss arena corners |
| `PROP_CHESTS` | 3 cells | Shop stock |
| `PROP_WARES` | 4 cells | Shop counter goods |
| `PROP_TORCH` | (0,9) (1,9) | Defined but currently unused |

Replacing the tileset without drawing these blanks them, and the failure is
silent: the gate colliders still work, so the room locks correctly with no
shutter visible, and the level-exit hatch simply disappears. `--check` now
parses `dungeon_map.gd` for these constants and fails if any cell it paints is
empty, so the trap cannot be re-set.

Two constraints on the props:

- They keep **transparent backgrounds** -- they sit on the floor rather than
  replacing it, and none carry collision.
- The gate is drawn as **horizontal slats on purpose**. `dungeon_map.gd`
  rotates it with `TRANSPOSE|FLIP_H` for openings in vertical walls, which
  turns the slats vertical -- and a vertical slat is what correctly bars a
  horizontal passage. One drawing serves both orientations.

### Regenerating: re-import or you are testing stale art

Godot serves the imported `.ctex`, not the PNG on disk. After running the
generator, run `godot --headless --path . --import` before testing, or the game
renders the previous version and you will debug a bug that no longer exists.

### Two traps, both hit during the build

- **Pattern phase must be cell-local.** The checker was first derived from the
  cell's atlas position. Because the renderer can drop either floor variant on
  any map coordinate, the pattern broke apart wherever two variants met. Phase
  from cell-local coordinates tiles correctly under any shuffle, because the
  pattern's period (16px) divides the tile size.
- **Variation must be a value shift, not an added mark.** A 3px grease pool on
  the second floor variant produced a visible grid of identical stamps once it
  repeated across a room. Darkening one quarry tile instead reads as texture.

`--check` enforces both: every pixel on-palette, grout continuous across every
floor join, and all twelve floor cells agreeing on one checker phase.

```bash
python tools/make_kitchen_tileset.py --preview --check
```

Retune the look by editing the named colour roles at the top of the script
(`FLOOR_A`, `WALL_BODY`, `TRIM`, ...) and re-running. Value structure is a
readability decision, not a taste one: dark warm floor, mid cool-grey walls,
so warm saturated sprites and projectiles read against both. The floor is
deliberately **not** red -- section 3 reserves `SAUCE_*` for enemy-owned
things, and a red floor would bury enemy bullets.

## 6b. Generated art -- done

12 Gemini-generated assets are in and wired up:

- **4 enemies** (48x48): `wing_trooper`, `saucy_wing`, `celery`, and
  `bucket_brute` (the wing boss, reusing its 48x48 art at integer `scale = 2`).
- **8 kitchen props**: `deep_fryer`, `heat_lamp`, `sauce_taps`, `sauce_vat`,
  `wing_warmer` (32x32), `mop_bucket`, `freezer_door` (32x48) and

That closed the game's biggest content gap: `RoomTheme` was
`{ NONE, BURGER, TACO, PIZZA }` with a slime/burger/taco/pizza roster, so a
chicken-wing game had no chicken in it. There is now a `WING` theme with its own
enemies, props and boss.

Still missing: the **extractor hood** (12 of the 13 assets came back), and the
UI pass in section 7.

### Two things generated art needs that hand-made art does not

- **`key_background`** -- generators return an opaque canvas.
- **`exclude_ramps: ["VIOLET"]`** -- keying leaves a blended rim on the outer
  silhouette that snaps to whatever palette ramp the key colour is nearest.
  With a magenta key that is `VIOLET`, and every prop comes out wearing a purple
  halo. A de-fringe pass removes most of it; excluding the ramp removes the
  rest, and costs nothing because `VIOLET_*` is reserved for boss/cursed/rare
  anyway. **Whatever key colour you use, exclude the ramp nearest to it.**

### Decoration placement

`DungeonDecorator` is footprint-aware, and the rules matter as much as the art.
A decoration is not a point on a tile: a 32x48 prop covers 2x3 tiles, and the
old code centred every sprite on a single cell, so tall props punched through
the wall above and hung over the floor below -- **28% of them clipped a wall**.

Each prop now declares only a `Placement`:

- `FLOOR` -- stands free, base on the bottom of its footprint.
- `WALL_BACKED` -- equipment that belongs against a wall (fryer, freezer door,
  sauce taps, ovens, vending machines). Requires rock directly above the
  footprint and is drawn touching it.

The footprint is derived from the texture, and a cell is only accepted when
every tile the sprite will physically cover is verified floor inside the room.
`tools/verify_decorations.gd` asserts this across 40 seeds and reports what the
old alignment would have done, so the guarantee is measured rather than assumed:

```bash
godot --headless --path . --script res://tools/verify_decorations.gd
```

## 6c. What still needs generating

Generate at any size and any quality, then run it through
`tools/conform_art.py` -- the generator only has to get silhouette and content
right, the pipeline enforces grid, palette and edges.

**Ready-to-paste prompts for all of this live in [art_prompts.md](art_prompts.md)**,
along with the shared style preamble, negative prompt and per-tool settings.

Generated art needs `"key_background": true` on its manifest group: image
generators return an opaque canvas, so without keying every asset arrives as a
solid rectangle. The keyer floods in from the border rather than matching an
exact colour, which survives the soft gradient a model puts in a "flat"
background and will not punch holes in matching colours inside the subject.

Free options, in order of usefulness for this project:

- **Local ComfyUI + SD1.5 + a pixel-art LoRA** on the GTX 1660 (6GB is
  comfortable for SD1.5; SDXL is tight). Free and unlimited. Its real advantage
  is **img2img at low denoise with a fixed seed**, which restyles existing
  animation frames while keeping them coherent frame-to-frame.
- **Google AI Studio (Gemini image generation)** -- free tier, no setup, and the
  strongest free option at *"match this reference style"*: feed it
  `assets/palette/wingpunk40.png` plus two or three existing sprites. Rate
  limited, so use it for hero assets like the tileset.
- Avoid general-purpose free image tiers for pixel art -- they produce soft
  edges and thousands of colours that the pipeline then has to fight.

## 7. Known exceptions

- **UI** (`assets/UI/`) is audited but never conformed. Menu buttons are 210x55
  with 7000+ colours and text baked into the texture; `panel.png` is 9-sliced;
  their sizes are coupled to Control layout. Quantising them to 40 colours would
  wreck the text and the 9-slice borders. Restyling the UI is a separate pass,
  and it is the largest remaining inconsistency after this one.
- `main_menu.tscn` draws `mascot_hero.png` (160px tall) at a
  `custom_minimum_size` of 180px, i.e. 1.125x -- off the grid. Setting that to
  160 makes it exact. Not changed here because it is a layout edit, not an art
  edit.
- **Unreferenced art**: 393 PNGs (374 status-effect frames, a spare bullet
  sheet, the crosshair, `player_idle.png`) plus ~180 files from the dungeon pack
  are referenced by nothing. They are audit-only. Wire them up or delete them.
- **Transient tween scales** (spawn/despawn punches on abilities, the shockwave
  shader's scale-14 UV carrier, `second_life`'s procedural glow polygons) are
  motion or non-texture nodes and are exempt from the integer-scale rule.

## 8. Workflow

```bash
# Drop raw generated art anywhere under assets/, add a manifest entry, then:
python tools/conform_art.py audit     # what is out of spec right now
python tools/conform_art.py conform   # downscale -> palette -> alpha -> canvas
python tools/conform_art.py verify    # exit 1 if anything violates this doc
python tools/conform_art.py scenes    # check .tscn scales are integral
```

`conform` is idempotent. On first touch it copies each original to
`assets/_source/` and always re-derives from there, so you can tweak the palette
or a target size and re-run without cumulative degradation. `assets/_source/`
is the art master (3.7 MB, 219 files) -- keep it in git.

`conform` reports every island that despeckling removed. **Read those lines.**
Despeckling is per-group for a reason: a tileset atlas is disconnected islands
by definition, and a global relative threshold silently deleted 30 tiles from
`New_tilemap.png` on an early run. It is off for `tileset` and opt-in
(`despeckle_fraction`) only for single-subject sprites like bullets.
